# Rust port: C++ quirks kept for parity

While the C++ implementation is the golden oracle, the Rust port reproduces
its output exactly, including behaviour that is arguably a bug. Each item is
marked `QUIRK(parity)` in the code. Revisit them once the oracle is retired.

| Where | Quirk |
|---|---|
| `LC_UUID` view | The UUID value row is never emitted (the C++ `AddRow` call resolved to an empty template overload). |
| `Load Commands` node | The byte range's address label is always 0 instead of the file offset. |
| `LC_SOURCE_VERSION` view | The 64-bit `A.B.C.D.E` version is formatted from its low 32 bits as `x.y.z`. |
| `LC_*_DYLIB` view | "Name" is empty when the path contains no `/`. |
| CPU subtype | arm64e (`CPU_SUBTYPE_ARM64E`) is not in the table, so the subtype rows are omitted. |
| Byte-swapped Mach-O | Only the header fields are swapped; load commands are read as little-endian. |
| `Section(...)` node | The "Section Name" and "Segment Name" rows are never emitted (same empty `AddRow` template overload as `LC_UUID`). |
| `Segment Split Info` node | Its display name is "Two Level Hints Table", the same as the real two-level hints node. |
| `String Table` / `Data in Code Entries` nodes | The byte range's address label is relative to the Mach-O header (`stroff` / `dataoff`), not the file, unlike the sibling nodes. Differs inside fat files. |
| `Function Starts` node | The ULEB128 list is not cut at its zero terminator; alignment padding shows up as extra rows repeating the last address. |
| `Symbol Table` node (32-bit) | `n_desc` is a signed short, so values with the top bit set print as `-<magnitude>` in hex. |
| `Symbol Table` node / `Integrity Report` | The symbol table byte size (`nsyms * sizeof(nlist)`) is truncated to 32 bits. |
| `Dynamic Symbol Table` node | The byte range covers only the first table present (toc, modtab, extrefsym, indirectsym, extrel, locrel), and its size wraps at 32 bits. |
| `Integrity Report` node | Offsets are compared as stored (relative to the Mach-O header) against the whole file size, so fat slices are checked against the wrong bound. |
| `.a` archive member names | The 16-byte name is trimmed of trailing `/` before it is compared, so the checks for `//` (GNU string table), `/` (symbol table) and BSD `#1/NN` long names never match: GNU `/NN` names stay unresolved, the symbol table is listed as a member with an empty name, and BSD long-name members keep the name `#1/NN` with the inline name left in the payload, so they are listed as `data` even when they hold a Mach-O. |
| `Dyld Shared Cache` view | There is no "Magic" row (the C++ `AddRow` call resolved to an empty template overload) and the Offset column of every header row is `00000000`. |
| `moex cache-list` | The `magic:` line / `"magic"` JSON value contains all 16 magic bytes, including the trailing NUL padding (unescaped in JSON). |
| `moex cache-extract --compact` | File offsets of 0 ("not present") in `LC_SYMTAB` / `LC_DYSYMTAB` / `LC_DYLD_INFO` / linkedit-data commands are remapped like real offsets, so they become the new offset of the segment that started at file offset 0. |
| `moex cache-extract` | The reported output size is computed with wrapping 64-bit arithmetic, so a segment with an absurd file offset does not grow it. |
| `Dynamic Loader Info` node | A child node exists when `offset * size > 0` computed in 32 bits, so a blob whose product wraps to zero gets no node. Rows of the four opcode tables and of `Export Info` have four cells under the three default headers. |
| `Rebase Info` node | Operand rows (`uleb128`) repeat the opcode's offset instead of the operand's own, and counts / skips are cut to a signed 32-bit integer. The walker's (undisplayed) running address drops the segment offset for 64-bit images. |
| `Binding Info` / `Weak Binding Info` / `Lazy Binding Info` nodes | No byte range. `BIND_OPCODE_SET_DYLIB_SPECIAL_IMM` prints its negative ordinal as an unsigned 64-bit number (-1 is `18446744073709551615`). `BIND_OPCODE_DO_BIND_ULEB_TIMES_SKIPPING_ULEB` is labelled `REBASE_OPCODE_DO_REBASE_ULEB_TIMES_SKIPPING_ULEB`, its operand rows repeat the opcode's offset with a `0x`-prefixed hex dump, and its values are cut to a signed 32-bit integer. Opcodes above `0xC0` (threaded binds) are skipped silently. |
| `Export Info` node (classic trie) | Not a faithful trie decoder: the terminal size is read as one byte instead of a ULEB128, and the child count is read right after the first two terminal values rather than at `terminal start + terminal size`, so re-export and stub-and-resolver nodes are misread. "Symbol Offset" is cut to a signed 32-bit integer. The in-file check uses the header-relative offset (too lax inside a fat file). No byte range. |
| `Exports Trie (LC_DYLD_EXPORTS_TRIE)` node | The Offset column and the byte range's address label are relative to the Mach-O header (`dataoff`), not the file. A re-export's import name loses its leading byte(s) because one ULEB128 is skipped before it (`_foo` shows as `foo`; an empty name shows as `<none>`). The terminal size is not range-checked, so a huge value wraps and the child list is read from before the node. |
| `Chained Fixups (LC_DYLD_CHAINED_FIXUPS)` node | Each segment's info offset is applied to the start of the blob instead of to `dyld_chained_starts_in_image`, and `page_start[]` is read at offset 24 of the struct instead of 22, so the segment, page and fixup rows usually decode unrelated bytes (typically as "UNKNOWN" format, 4-byte `fixup32` rows). Fixup locations are used as plain file offsets (no fat slice offset, no VM translation); the "next" field uses one layout per pointer width with a fixed 4-byte stride; field offsets (`dataoff + n`) wrap at 32 bits; the byte range's address label is `dataoff`. |
| `Section(...)` content views (all) | Each view's byte range is the section *header* (same as its parent node), not the section contents. |
| `Section(...)` ObjC views | Only sections of a segment named exactly `__DATA` (or legacy `__OBJC2`) get the class / category / protocol metadata, class-refs, super-refs and image-info views; `__DATA_CONST` / `__DATA_DIRTY`, where current linkers put them, get none. |
| `ObjC CFStrings`, `ObjC2 Class/Super References`, `ObjC2 Image Info` | The first column is always `00000000` (the table has no offset resolver). The CFString and reference tables carry the headers `Index, Offset, Length, String` over three-cell rows. |
| `ObjC2 * Metadata` | Relative method lists (`entsize` flag `0x80000000`) show `entsize=2147483660` and no methods; `Method` rows have byte length 0; an ivar's offset variable is read as a pointer-sized word; chained-fixup / authenticated pointers are not decoded, so on arm64 most targets show as `unmapped`. |
| ObjC / Swift metadata readers | A virtual address is translated with the segment's `fileoff` taken from the start of the file, not of the Mach-O header, so inside a fat file the wrong bytes are read. |
| `Disassembly (Capstone)` | Decoding stops at the first bytes that are not an instruction (no data skipping); 32-bit ARM is always decoded in ARM mode, never Thumb; an empty or undecodable section gives the row `Disassembly failed: OK (CS_ERR_OK)`; message rows have four cells in a five-column table. |
| `Disassembly (Capstone)` "Symbol" | Symbols are sorted by address with the non-stable `std::sort`; which of several symbols at one address names the following instructions (`name+0x..`) is an artefact of libc++'s introsort, reproduced by `macho::libcxx_sort`. The address itself gets the last such symbol in table order. |
| `Disassembly (Capstone)` "Notes" | `LC_DATA_IN_CODE` offsets (relative to the Mach-O header) are compared with file offsets; `LC_FUNCTION_STARTS` is cut at its first zero here, unlike in the `Function Starts` node. |
| `Swift Metadata` | Every `__swift5_*` view ends with the image's whole Swift symbol list. Names are demangled by running `xcrun swift-demangle` (macOS only; elsewhere only the leading `<len><ident>` components are decoded). A final unterminated `__swift5_reflstr` string is listed with a byte length one past the section. |
| `Swift Semantic Graph` | Strings go to the demangler between unescaped single quotes, so embedded quotes vanish (`XPC error '%@'` → `XPC error %@`); context kind 4 (opaque type) is `unknown`; a zero relative pointer is an edge from the entry to itself; the `__swift5_fieldmd` cursor skips the declared record table even when it is truncated. |
| `Xref Report` node | The disassembly sweep of `__TEXT,__text` ends at the first bytes Capstone 5 does not decode (on x86 usually the first jump table), so code after that point contributes no references. `macho/xref/{a64,x86}.rs` reproduce what Capstone accepts, its instruction lengths and its jump/call groups (`loop*`, `ret` and `bc.cond` are not jumps; `bl`/`blr` are both jump and call). |
| `Xref Report` node | Capstone's operand-access table is reproduced as is: e.g. arm64 `cmp`/`cmn`/`tst` "write" their first operand, `svc` writes x30, LSE atomics and 32-bit `adds #imm` write nothing; x86 `test eax, imm32` writes eax, 16-bit pushes/pops name esp, `stosq` writes rcx. Different widths of one register (`x8`/`w8`, `rax`/`eax`) are tracked as unrelated registers. |
| `Xref Report` node | A register an instruction writes is forgotten before the instruction's own address pattern is applied, so `adrp x8` + `add x8, x8, #off` (and x86 `add reg, imm`) never completes an address; only patterns into a different register do. |
| `Xref Report` node (arm64) | Every immediate operand of a branch is reported as a target, including the bit number of `tbz`/`tbnz`; every register operand with a known value too (e.g. the register tested by `cbz`). `movk` ignores its shift, `movz` is never followed, and a register-indexed `ldr` is followed as if it read `[base]`. Loads always read 8 bytes. |
| `Xref Report` node | Pointer reads behind `ldr`, `mov reg, [rip+x]`, `call/jmp [mem]` use the segment's `fileoff` as an offset into the whole file, so inside a fat file they read from the wrong place. |
| `Xref Report` node | 32-bit ARM code is disassembled by the C++ implementation but nothing is taken from it; only pointer sections are reported for such slices. |

## Intentional differences from the C++ implementation

| Where | Difference |
|---|---|
| Symbol Table "Demangled" row | macOS uses the system `libc++abi` demangler (identical to C++). Linux and Windows use the `cpp_demangle` crate, whose text can differ for heavily templated names. |
| `moex cache-list --limit=X`, `moex cache-extract --max=X` | A non-numeric value is a usage error (exit 2); the C++ tools aborted on the uncaught `std::stoi` exception. |
| `moex cache-extract` write failures | A failed write, an output size the filesystem rejects, or a segment whose target offset wraps is reported (`cannot write output file: ...` / `segment target out of range: ...`, exit 1) and the partial file is removed; the C++ tool ignored stream errors and reported success. |
| `moex cache-extract` hostile segment sizes | A segment whose `source offset + size` overflows 64 bits is rejected with `segment source out of range`; the C++ check wrapped and the tool then crashed. Load command sizes are accumulated in 64 bits for the same reason. |
| `moex cache-list` / `cache-extract` / `diff` usage text | The usage line names the program as `moex <subcommand>` instead of `moex-<tool>`; error prefixes such as `moex-cache-list failed:` are unchanged. |
| dyld cache `.map` fallback | Lines longer than 64 KiB are cut at 64 KiB. |
| Empty file | Reports `File is empty`; the C++ tool reported `Can not open file` because mapping a zero-length file failed. |
| Text dump, non-UTF-8 cell bytes | Each invalid byte is written as `?` (same as the JSON dump always did); the C++ text dump wrote the raw byte. |
| `Rebase Info`, unknown opcode | Skipped silently. The C++ walker hits `assert(false)`: a debug build (including the `moex-dump` oracle) aborts, a release build skips it. |
| `Dynamic Loader Info` out-of-file reads | Where the C++ pointer arithmetic left the mapped file (a chained fixup offset that wraps around 64 bits, a classic export trie that passes the lax fat-file check, a modern trie position that wraps to before the start of the file) the behaviour was undefined; the walk stops at that point instead. |
| `Dynamic Loader Info` size limits | Hostile inputs are bounded where the C++ walk was not: the chained fixups starts walk stops after 1,000,000 rows or 8,000,000 steps (the imports table is still listed), a trie walk stops after 500,000 edges (and the modern one after 256 MiB of accumulated names), and an opcode stream after 8,000,000 opcodes. No well-formed binary reaches these. |
| `Floating Point Literals` (`S_4BYTE/8BYTE/16BYTE_LITERALS`) | The C++ aborts (`std::bad_function_call`) on any non-empty literal section, taking the whole dump with it. Rust lists `offset, "Floating Point Number", hex bytes`, which is what that code was written to produce. |
| `Literal Pointers`, `Module Init/Term Func Pointers` | The C++ prints `<address of the entry in its own memory mapping>-><value>`, different on every run (ASLR). Rust prints the entry's file offset (that address minus the mapping base). The golden baselines hold one run's addresses, so these cells can only be compared after subtracting the base. |
| Swift demangling | The C++ runs one `sh -c "xcrun swift-demangle '<name>'"` per name. Rust starts the tool directly (no shell), many names per invocation, and never passes names beginning with `-` or `@` (option / response file). In the Swift Semantic Graph, where the C++ does not escape quotes, a name whose quoting would make the shell split words or run commands is not passed at all (the C++ would execute it). `MOEX_NO_SWIFT_DEMANGLE=1` disables the tool. |
| `ObjC2 * Metadata` limits | At most 2,000,000 rows per table (then a `... / row limit reached` row) and about 100 levels of protocol nesting; the C++ has no bound and can be made to run out of memory or stack by a crafted file. |
| Reads past the end of the file | `objc_image_info` at a section offset outside the file gives no rows, and a Swift context descriptor cut off by the end of the file reads as zeros; the C++ reads out of bounds. |
| Capstone version | Rust bundles Capstone 5.0.6 (`capstone` crate 0.14); the C++ oracle used Homebrew 5.0.9. Same options (default syntax, detail off, no SKIPDATA). No instruction text differed on any compared binary (arm64/arm64e, x86_64, armv7). |
| `Xref Report` node | Work is bounded: at most 4x the file size is scanned per Mach-O header (only reachable when crafted sections alias the same bytes; C++ scans each in full), and a pointer read that falls outside the file fails instead of reading out of bounds. |
| `Xref Report` node | The sweep does not use the bundled Capstone 5.0.6 but private decoders that match the oracle's Capstone 5.0.9 (the two differ: 5.0.6 rejects the x86-64 `movsxd r32, r/m32` encoding `63 /r` without REX.W, which ends a sweep early). They match 5.0.9 exactly on everything tested (see the module docs of `macho/xref.rs`), with known gaps in corners that real code does not reach: a few EVEX encodings whose validity depends on masking together with other prefix bits, and 32-bit x86 near jumps under a 67 prefix. Such bytes can only be met as data inside `__text`, where they may end the sweep a little earlier or later than Capstone did. |
